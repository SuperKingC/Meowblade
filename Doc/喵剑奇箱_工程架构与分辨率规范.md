# 《喵剑奇箱》工程架构与分辨率规范

## 1. 目标

当前工程不再按一次性原型组织，而是以可扩展到中型 2D 放置军团游戏为目标建立基础边界。

本次架构调整重点不是一次性建立庞大的通用框架，而是先保证：

- 玩法规则与 Unity UI 表现解耦；
- 存档实现可以替换和测试；
- 系统时间可以替换，便于离线收益和时间异常测试；
- Runtime 与 Editor 代码具有程序集边界；
- 后续增加配置表、资源加载、任务、活动和网络服务时有稳定落点；
- Demo 阶段仍能快速修改玩法，不被过度抽象拖慢。

## 2. 目录结构

```text
Assets/
├─ Meowblade/
│  └─ Scenes/
│     └─ MeowbladeDemo.unity
└─ Scripts/
   ├─ Runtime/
   │  ├─ Meowblade.Runtime.asmdef
   │  ├─ Core/
   │  ├─ Application/
   │  ├─ Infrastructure/
   │  ├─ Gameplay/
   │  └─ Presentation/
   └─ Editor/
      ├─ Meowblade.Editor.asmdef
      └─ ProjectTools.cs
```

脚本已经从 `Assets/Meowblade/Scripts` 迁移到 `Assets/Scripts`。所有原有 `.meta` 与脚本一起移动，场景中 `AppBootstrap` 的 MonoScript GUID 保持不变。

文件名、公开类型名和命名空间已去掉 `Demo` 前缀。产品仍然可以称为 Demo，但工程代码不再把“Demo”当成系统类型的一部分。

## 3. 分层职责

### 3.1 Core

`Runtime/Core` 放置不依赖具体界面流程的核心数据定义：

- 资源、岗位、英雄、关卡等稳定标识；
- 存档 DTO；
- 战斗属性结构；
- 当前默认平衡数值；
- 参考分辨率和宽高比。

Core 不应直接访问：

- Canvas、Button、Text；
- 文件系统；
- UnityEditor；
- 具体场景对象。

当前 `GameBalance` 仍是静态配置，这是为了保持玩法打磨速度。进入中期内容制作后，应将英雄、敌人、关卡、配方和建筑配置迁移为 ScriptableObject 或外部表格生成的数据对象。

### 3.2 Application

`Runtime/Application` 负责组织用例和运行时服务。

主要对象：

- `GameContext`：应用组合根，集中创建并连接服务；
- `GameSession`：当前玩家会话和核心用例入口；
- `ISaveRepository`：存档仓储接口；
- `IClock`：时间来源接口；
- `SystemClock`：真实系统时间实现。

UI 不再直接决定存档路径，也不直接创建文件存档类。启动时由 `GameContext` 组合依赖，再向界面提供 `GameSession`。

编辑器自检可以为 `GameContext` 指定独立测试存档路径，因此不会覆盖玩家正常存档。

### 3.3 Infrastructure

`Runtime/Infrastructure` 放置与设备、文件、平台或第三方 SDK 有关的实现。

当前包含：

- `JsonSaveRepository`；
- UTF-8 JSON 写入；
- `.tmp` 临时文件；
- `.bak` 备份文件；
- 主存档损坏时读取备份。

后续可以在这一层增加：

- PlayerPrefs 轻量设置；
- 云存档适配器；
- Addressables 资源加载器；
- 本地通知；
- 登录、支付、广告和数据统计 SDK 适配器；
- 网络请求和版本更新服务。

### 3.4 Gameplay

`Runtime/Gameplay` 放置具体玩法模拟。

当前 `BattleSimulation` 独立维护：

- 单位生成；
- 移动和索敌；
- 普攻与技能；
- Boss 机制；
- 号令；
- 胜负；
- 临时战损。

它不创建 UI，也不直接保存结果。胜利结果通过 `BattleResult` 交给 `GameSession` 决定是否提交。

后续建议按功能扩展：

```text
Gameplay/
├─ Battle/
├─ Production/
├─ Formation/
├─ Equipment/
├─ Progression/
├─ Quests/
└─ Events/
```

当生产、养成和装备规则明显扩大时，再从 `GameSession` 抽出对应服务。当前规模下保留统一会话入口，可以减少无意义的跨服务通信。

### 3.5 Presentation

`Runtime/Presentation` 负责 Unity 场景、UI、动画和反馈。

当前界面只做：

- 读取 `GameSession` 和 `BattleSimulation` 状态；
- 将用户点击转为应用用例调用；
- 创建和更新 UGUI；
- 显示 Toast、弹窗、血条、伤害数字和战斗预警。

正式美术接入后，可以把程序化 UGUI 替换为 Prefab、Animator、Spine 和 Timeline，而不改变生产、存档和战斗核心规则。

## 4. 程序集边界

当前程序集关系：

```text
Meowblade.Editor
       ↓
Meowblade.Runtime
       ↓
Unity Engine / Unity UGUI
```

作用：

- 编辑器工具不会被打入 Player；
- 修改 Editor 工具时不必重新编译全部 Runtime；
- Runtime 不能误引用 UnityEditor；
- 后续可以继续拆分 `Meowblade.Gameplay`、`Meowblade.Infrastructure` 和测试程序集。

现阶段只建立 Runtime/Editor 两个程序集，避免在不足十几个脚本时拆成过多 DLL。系统数量增加后，再根据稳定依赖方向细分。

## 5. 启动流程

```text
场景加载
→ 检查/创建 Main Camera
→ 检查/创建 AppBootstrap
→ GameContext 创建服务
→ JsonSaveRepository 读取存档
→ GameSession 校验与应用离线收益
→ 创建 Canvas/EventSystem
→ 进入 HomeScreen
```

场景中已经放置主相机和 `MeowbladeBootstrap`。运行时仍保留相机和 Bootstrap 兜底，因此更换场景、误删相机或直接从测试场景启动时，不会再出现运行后没有相机的情况。

## 6. 分辨率与宽高比

### 6.1 设计基准

- 参考分辨率：`1920 × 1080`
- 参考宽高比：`16:9`
- CanvasScaler：`Scale With Screen Size`
- Match Width Or Height：`0.5`
- 目标方向：横屏

在 `1920×1080` Game 视图下可以看到和设计坐标完全一致的画面。

### 6.2 完整等比体验范围

所有 16:9 分辨率都可以等比体验：

| 分辨率 | 用途 |
|---|---|
| 1280×720 | 低配 Windows、性能验证 |
| 1600×900 | 普通桌面窗口 |
| 1920×1080 | 设计与验收基准 |
| 2560×1440 | 高分辨率桌面 |
| 3840×2160 | 4K 缩放检查 |

### 6.3 手机超宽屏

18:9、19.5:9 和 20:9 会比参考画面多出左右区域。当前功能 UI 的关键按钮都位于 16:9 安全区内，可以正常使用，但正式美术需遵循：

- 背景原画至少提供 20:9 横向延展；
- 关键角色、建筑和文字保持在中央 16:9 安全区；
- 最外侧区域只放可裁切背景、装饰或氛围光；
- 刘海、圆角和系统手势区使用 Unity `Screen.safeArea` 做最终适配；
- 弹窗宽度不超过安全区宽度的 80%；
- 战斗 HUD 不贴设备物理边缘。

推荐场景美术母版尺寸为 `3200×1440`，中央 `2560×1440` 作为主要安全构图；UI 仍按 `1920×1080` 标注和切图。

## 7. 下一阶段架构扩展顺序

玩法继续扩大时，建议按以下顺序建设：

1. 将平衡数值迁移到 ScriptableObject/表格配置；
2. 建立统一资源加载接口和 Addressables 分组；
3. 将 UI 从程序化创建迁移到 Prefab + Presenter；
4. 增加场景流程和异步加载状态机；
5. 将生产、装备、任务从 `GameSession` 拆成独立应用服务；
6. 增加本地化、红点、引导、音频和对象池；
7. 建立 EditMode/PlayMode 自动测试程序集；
8. 接入云存档、登录、数据统计、广告和支付适配层。

不建议现在就引入大型 DI 容器、完整 ECS 或复杂消息总线。当前 `GameContext` 的显式组合更容易调试，也足以支持本阶段向中型项目演进。
