# Graybox Baseline v0.1 设计规格

日期：2026-08-05
状态：已批准（2026-08-06）
适用工程：`Meowblade` / Unity `2022.3.62f3`

## 1. 决策与目标

本阶段采用“先固化灰盒基线，再进行核心闭环试玩”的推进方案。

目标不是增加玩法内容，而是把当前已经实现的灰盒 Demo 变成一个：

- 可以从 Git 完整恢复；
- 可以通过命令重复编译、测试、构建和冒烟验证；
- 关键领域规则具有自动回归保护；
- 战斗结算不会因 UI 重入或生命周期重入重复发奖；
- 可以交给未读过设计文档的玩家进行有效试玩判断；
- 试玩未通过时可以低成本修改，而不被正式美术投入绑住。

阶段完成后，项目仍是灰盒 Demo。核心玩法是否成立，要由后续真实试玩结果决定，不能仅凭自动测试宣告成立。

## 2. 当前事实基线

当前工程已经实现：

- 三资源和三岗位在线生产；
- 三只工人猫的岗位分配；
- 离线生产和 JSON 主/备份存档；
- 猫窝治疗、补员和纸箱侠披风；
- 3x2 编队、普通关、Boss、号令和战损回城；
- Boss 首通后全局生产倍率提升；
- 程序化 UGUI 主界面、编队、战斗和结算界面；
- 编辑器自检与 Windows Player UI 冒烟入口。

现有 2026-08-05 日志显示默认主路径曾通过自检，普通关约 9.4 秒，Boss 约 36.2 秒。该日志是历史证据，不代替本阶段完成后的新鲜验证。

当前已知缺口：

- 场景、脚本、文档、概念图和必要 `.meta` 尚未形成 Git 基线；
- 没有 Unity Test Framework 测试程序集；
- `BattleResult` 没有唯一结算 ID，重复提交会再次发放重复通关奖励；
- Player 冒烟日志包含 missing script 警告；
- 现有 Player 冒烟只验证界面对象存在，不验证日志洁净度和主要交互流；
- 现有自检直接补满资源，不能证明真实经济节奏满足 6～8 分钟闭环；
- 猫宅概念图尚未进入运行时，当前仍使用程序化占位表现。

## 3. 范围

### 3.1 本阶段包含

1. 建立可恢复的源码和资源基线。
2. 修复战斗结果重复提交问题。
3. 建立 EditMode 自动测试程序集和关键测试替身。
4. 将现有编辑器自检保留为端到端快速诊断。
5. 建立可重复执行的 Windows 构建和 Player 冒烟入口。
6. 消除 fresh build 中的 missing script、编译异常和运行时异常。
7. 更新运行说明，使“历史验证”和“可重复验证命令”区分清楚。
8. 准备核心闭环试玩记录模板和通过门槛。

### 3.2 本阶段不包含

- 正式角色、敌人、岗位、场景或 UI 美术接入；
- Spine、逐帧动画、音效、音乐、特效或镜头表现；
- 新关卡、新装备、新资源、新建筑或长期成长；
- ScriptableObject 配置迁移；
- Addressables、DI 容器、ECS、消息总线或大规模服务拆分；
- Android SDK 安装、正式 APK/AAB 交付或真机性能调优；
- 云存档、登录、统计、广告和支付；
- 以测试覆盖率百分比为目标的无差别补测。

Android 技术冒烟是灰盒试玩后的紧邻事项，但不是本基线的完成条件。

## 4. 版本控制基线

需要纳入 Git：

- `Assets/Scripts/**` 及全部必要 `.meta`；
- `Assets/Meowblade/Scenes/MeowbladeDemo.unity` 及 `.meta`；
- `Assets/Art/Concept/VisualDirection/**` 及 `.meta`；
- `Doc/**` 中当前 Demo、架构、运行和美术说明；
- `Packages/manifest.json` 与 `Packages/packages-lock.json`；
- 本阶段新增的测试、工具、试玩模板和规格；
- 必要的 `ProjectSettings/**`；
- `.gitignore` 中的项目级忽略规则。

不得纳入 Git：

- `Library/`、`Temp/`、`Logs/`、`Builds/`、`UserSettings/`；
- `.unitycowork/`；
- 本地 IDE 工程文件；
- 临时测试存档和 Player 持久化测试数据。

基线提交前必须使用 `git status` 和 `git diff --check` 检查目标文件，不能顺带纳入与本阶段无关的本地数据。

## 5. 战斗结算幂等设计

### 5.1 数据契约

`BattleResult` 增加非空唯一结算 ID 字段 `SettlementId`。每次创建一场新的 `BattleSimulation` 时生成一次 ID；同一场战斗产生的结果始终使用同一个 ID。战斗数值模拟仍使用固定随机种子，唯一 ID 不参与索敌、伤害、暴击或掉落计算，因此不会破坏战斗确定性。

`GameSaveData` 增加已提交结算 ID 集合。考虑到当前 Demo 只有两个关卡和少量试玩次数，v0.1 使用可序列化的字符串列表即可，不引入数据库或复杂裁剪策略。

旧存档中该字段为 `null` 时，`EnsureStateIsValid` 将其初始化为空列表，保证存档向前兼容。

### 5.2 提交规则

`CommitBattleResult` 返回本次结果是否实际提交：

- `null` 结果：拒绝；
- 失败结果：拒绝，不写入结算 ID，不提交战损，不发奖励；
- 空结算 ID：拒绝并记录明确错误；
- 已处理的结算 ID：直接拒绝，不改变任何状态；
- 首次提交的胜利结果：应用战损、首通或重复通关奖励，将 ID 加入已处理集合，然后保存完整状态。

同一个 `BattleResult` 对象重复提交、或重建出相同结算 ID 的结果再次提交，都必须保持资源、战损、关卡和生产倍率不变。

本阶段不改变“不同战斗可以获得重复通关奖励”的现有规则。幂等只针对同一结算被重复提交，不禁止玩家重新挑战关卡。

## 6. 自动测试设计

### 6.1 测试边界

新增 `Assets/Tests/EditMode/Meowblade.EditModeTests.asmdef`，引用 `Meowblade.Runtime` 和 Unity Test Framework。`Packages/manifest.json` 将测试框架列为直接开发依赖，避免只依赖其他包的传递依赖。

测试使用：

- `InMemorySaveRepository`：验证应用规则而不写磁盘；
- `FakeClock`：精确控制离线时长和时间倒退；
- 临时目录中的 `JsonSaveRepository`：只验证真实 JSON、临时文件和备份恢复；
- 固定步长战斗驱动器：验证普通关和 Boss 的确定性结果。

每个测试独立创建状态，不读取或覆盖正常试玩存档。

### 6.2 必须覆盖的用例

库存与消费：

- 添加资源不超过容量并返回实际添加量；
- 材料不足时多资源消费不产生部分扣除；
- 消费后满仓岗位可以继续生产；
- 满仓期间不暗中累积可立即爆发的整数产物。

工人和在线生产：

- `3/0/0` 合法；
- 负数、单岗位超过 3、总数超过 3 均拒绝；
- 非法提交不改变原分配；
- 1、2、3 名纸板工人的产量与预览公式一致；
- Boss 首通倍率只应用一次且产量为 1.3 倍。

离线生产：

- 时间倒退按 0 秒处理；
- 少于最小展示时间不重复发放或显示无效面板；
- 超过 30 分钟按 30 分钟处理；
- 使用保存时的工人分配和生产倍率；
- 受库存上限约束并正确报告满仓；
- 初始化保存时间后，同一离线区间不会再次结算。

猫窝与工坊：

- 只有 `Injured` 可以治疗；
- 只有 `Empty` 可以补员；
- 治疗、补员成本正确并具有原子性；
- 普通关前不能制作披风；
- 披风首次制作扣费，已制作后重新装备不重复扣费。

战斗与结算：

- 默认编队能完成普通关；
- 准备充分且使用号令时能完成 Boss；
- 失败结果不提交战损或奖励；
- 首次普通关和 Boss 奖励只触发一次；
- 相同结算 ID 重复提交不重复发奖或战损；
- 两个不同结算 ID 的重复通关仍各自获得正常重复关奖励；
- Boss 生产倍率不会因重复结算叠加。

存档：

- JSON 保存后可以重载关键状态；
- 主存档损坏时可以读取有效备份；
- 缺失列表、越界资源、非法工人总数和短缺阵型可以安全修复；
- 旧存档缺少已提交结算列表时可以正常升级。

### 6.3 自检定位

`Meowblade -> Run Self Checks` 继续保留，用于快速运行完整默认路径并输出易读诊断。它不是单元测试替代品，不再作为所有边界正确性的唯一证据。

## 7. 可重复验证流程

### 7.1 编辑器入口

编辑器工具提供独立的命令行方法：

- 只运行领域自检；
- 构建 Windows x64 Player；
- 构建失败时返回非零退出码；
- 不要求每次验证都重新生成或改写场景。

仓库新增统一入口 `Tools/Verify-Graybox.ps1`。脚本接收 Unity Editor 路径，依次执行：

1. EditMode tests；
2. 领域自检；
3. Windows x64 fresh build；
4. Windows Player 多分辨率冒烟；
5. 汇总退出码和关键日志。

脚本不得删除仓库源码或用户存档，只能覆盖被 `.gitignore` 排除的本地测试日志和 `Builds/Windows` 构建目录。

### 7.2 Player 冒烟

冒烟运行使用隔离的测试存档，不读取或修改正常玩家存档。至少验证：

- 主相机存在且启用；
- 猫宅主界面创建；
- 打开分工面板并完成一次合法分配；
- 进入编队界面；
- 进入战斗界面；
- 中文字体能显示关键字；
- 核心按钮与文本存在；
- 退出码为 0。

分辨率矩阵：

- 1280x720；
- 1920x1080；
- 2560x1440；
- 2340x1080。

日志验收不只搜索 `PASSED`，还必须确认不存在：

- `The referenced script ... is missing`；
- `MissingReferenceException`；
- `NullReferenceException`；
- C# 编译错误；
- 冒烟测试的 `FAILED` 标记。

## 8. 文档与运行说明

更新 Demo 运行说明时必须明确区分：

- 当前代码在本次 fresh verification 中实际通过的项目；
- 旧日志中的历史结果；
- 尚未验证的 Android、真机性能和外部试玩结论。

运行说明提供可复制执行的验证命令、预期产物路径和失败日志位置。`Builds/` 和 `Logs/` 保持为本地生成物，不把二进制构建提交到源码仓库。

## 9. 核心闭环试玩

### 9.1 前提

只有 Graybox Baseline v0.1 的自动验收全部通过后，才开始 Playtest 01。试玩不是自动测试的一部分，需要 3～5 名未读过设计文档的真实玩家参与。

每名玩家：

- 使用重置后的独立存档；
- 不接受玩法口头讲解；
- 从首次进入猫宅开始；
- 直到击败 Boss 回城，或玩家明确无法继续；
- 记录屏幕、操作时间点、疑问和错误路径，但不在当场引导修正。

### 9.2 观察指标

必须记录：

- 是否在 10 秒内理解猫在生产资源；
- 是否理解工人总数只有 3；
- 是否能预测一次重新分工后的资源变化；
- 第一关后是否主动治疗、补员或查看披风；
- 是否理解披风、前后排和号令对 Boss 重压的作用；
- 从开始到 Boss 回城的总时长；
- 所有超过 15 秒且没有观察价值或决策的等待；
- 失败点、误触点、需要研究者解释的文本和反馈。

### 9.3 进入视觉切片的门槛

满足以下条件后，才进入正式视觉切片规格：

- 至少 4 名有效参与者，或 3 名参与者给出高度一致的结果；
- 多数玩家无需讲解即可完成一次工人重新分配；
- 多数玩家能说出重新分配对至少一种资源速度的影响；
- 多数玩家在第一关后主动完成治疗、补员或披风制作中的至少一项；
- 多数玩家理解至少一种 Boss 克制手段；
- 完整成功流程中位数为 6～8 分钟；
- 不存在系统性超过 15 秒的无意义等待；
- 没有阻断流程的存档、结算或界面错误。

如果门槛未满足，只调整生产节奏、信息层级、操作反馈、战损包装和 Boss 克制关系。不得通过增加新系统、新资源或新关卡掩盖问题。

## 10. 阶段完成标准

Graybox Baseline v0.1 完成必须同时满足：

- 当前 Demo 所需源码、场景、文档、概念图和 `.meta` 已形成 Git 基线；
- EditMode 测试全部通过且结果文件可读取；
- 编辑器领域自检通过；
- Windows x64 fresh build 成功；
- 四种分辨率 Player 冒烟均以退出码 0 结束；
- fresh build 和 Player 日志没有 missing script、编译错误或未处理异常；
- 相同战斗结算 ID 的重复提交测试通过；
- 正常玩家存档未被测试覆盖；
- 运行说明反映本次实际验证结果；
- Playtest 01 记录模板已准备完成。

自动验收完成只表示工程基线成立。只有第 9 节的真实试玩门槛通过，才能表示当前核心闭环值得进入正式视觉生产。

## 11. 风险控制

| 风险 | 控制方式 |
|---|---|
| 补测试演变成架构重写 | 只增加测试替身和必要注入点，不拆现有 `GameSession` |
| 幂等逻辑阻止正常重复挑战 | 只按唯一结算 ID 去重，不按关卡 ID 去重 |
| 自动验证污染试玩存档 | 自检、EditMode 和 Player 冒烟全部使用隔离路径 |
| 冒烟只看 `PASSED` 掩盖警告 | 同时扫描退出码、missing script 和异常关键字 |
| 为了视觉效果提前接入烘焙角色背景 | 本阶段保留概念图，不接运行时；后续要求背景和角色分层 |
| 基线提交混入缓存或二进制 | 提交前按白名单检查，并保持 `Builds/`、`Logs/` 被忽略 |
| 试玩样本太少却得出强结论 | 保留逐人观察记录，样本不足时只形成假设，不宣告玩法成立 |
